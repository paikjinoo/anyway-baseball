# Anyway Baseball ⚾

브라우저에서 즐기는 3D 야구 게임. Next.js + Three.js로 만들었고 Vercel에 배포합니다.

- **직접 하는 것**: 투구(구종 + 코스 선택), 타격(조준 + 타이밍), 도루 지시, 투수 교체, 대타·대주자·대수비
- **키우는 것**: 선수별 경험치 → 레벨 → 훈련 포인트, 골드로 티어(C/B/A/S) 강화·구종 습득
- **모으는 것**: 상점에서 골드로 선수 영입(뽑기), 필요 없는 선수는 방출
- **남는 것**: 경기마다 박스스코어와 결정적 장면 다시 보기, 시즌 기록 → 통산 기록과 타이틀
- **자동으로 되는 것**: 수비, 주루
- **모드**: **연습 타석** / CPU 대전 / 온라인 1:1 / **2대2 올스타전** / **2~7인 릴레이 타격 대결** / 리그(정규 시즌 + **포스트시즌**)
- **네트워크**: 로그인·팀·방 정보만 Firebase, 실제 경기 데이터는 **WebRTC P2P**로 직접 교환

---

## 빠른 시작

```bash
npm install
npm run dev
```

`http://localhost:3000` 접속 → **게스트로 둘러보기** → **팀 창단** → **CPU 대전**.

Firebase 설정 없이도 로컬 모드로 모든 싱글 기능(팀 편집, 훈련·성장, 리그, CPU 대전)을 쓸 수 있습니다.
한 계정에 팀은 하나입니다 — 골드와 아이템이 팀에 붙어 있어서, 팀을 여러 개 만들 수 있으면
지갑을 늘려 보상을 중복으로 모을 수 있게 됩니다.
데이터는 브라우저 `localStorage`에 저장됩니다. 온라인 대전만 Firebase가 필요합니다.

## Firebase 설정 (구글 로그인 + 온라인 대전)

1. [Firebase 콘솔](https://console.firebase.google.com)에서 프로젝트를 만듭니다.
2. **Authentication → Sign-in method → Google**을 사용 설정합니다.
   - 승인된 도메인에 `localhost`와 배포 도메인(`your-app.vercel.app`)을 추가합니다.
3. **Firestore Database**를 만듭니다 (프로덕션 모드).
4. **프로젝트 설정 → 내 앱 → 웹 앱 추가**에서 설정값을 복사합니다.
5. 프로젝트 루트에 `.env.local`을 만들고 `.env.example`을 참고해 채웁니다.

```bash
cp .env.example .env.local
```

```env
NEXT_PUBLIC_FIREBASE_API_KEY=AIza...
NEXT_PUBLIC_FIREBASE_AUTH_DOMAIN=your-app.firebaseapp.com
NEXT_PUBLIC_FIREBASE_PROJECT_ID=your-app
NEXT_PUBLIC_FIREBASE_STORAGE_BUCKET=your-app.appspot.com
NEXT_PUBLIC_FIREBASE_MESSAGING_SENDER_ID=1234567890
NEXT_PUBLIC_FIREBASE_APP_ID=1:1234567890:web:abcdef
```

6. `firestore.rules`의 내용을 Firestore 규칙에 붙여넣고 게시합니다.

### TURN 서버 (선택)

STUN만으로 대부분 연결되지만, 대칭형 NAT 환경(일부 회사망/모바일)에서는 TURN이 필요합니다.
[Metered](https://www.metered.ca/tools/openrelay/), [Twilio](https://www.twilio.com/stun-turn) 등에서
자격 증명을 받아 `.env.local`에 넣으면 자동으로 사용합니다.

```env
NEXT_PUBLIC_TURN_URL=turn:your-turn-server:3478
NEXT_PUBLIC_TURN_USERNAME=...
NEXT_PUBLIC_TURN_CREDENTIAL=...
```

## 홈 화면에 설치 (PWA)

`src/app/manifest.ts` 하나로 끝납니다 — Next가 `<link rel="manifest">`를 자동으로 넣어 주므로
`layout.tsx`에는 manifest를 적지 않습니다(두 군데에 두면 값이 갈라집니다). iOS는 공유 →
"홈 화면에 추가", 데스크톱 Chrome은 주소창의 설치 아이콘으로 설치합니다.

아이콘은 `public/icon.svg`가 원본이고, PNG는 거기서 한 번 굽습니다. **maskable은 별도
파일입니다** — 안드로이드가 적응형 아이콘의 바깥 20%를 깎아 내므로 같은 파일을 쓰면 공이
잘립니다. iOS용 `apple-touch-icon.png`는 배경을 미리 깔아 둡니다(투명 픽셀을 검게 칠합니다).

```bash
node -e "const s=require('./node_modules/.pnpm/sharp@0.34.5/node_modules/sharp');const p=(i,o,z)=>s(i,{density:512}).resize(z,z).png({compressionLevel:9}).toFile(o);p('public/icon.svg','public/icon-192.png',192);p('public/icon.svg','public/icon-512.png',512);p('public/icon-maskable.svg','public/icon-maskable-512.png',512);s('public/icon-maskable.svg',{density:512}).resize(180,180).flatten({background:'#030806'}).png().toFile('public/apple-touch-icon.png')"
```

`density: 512`가 핵심입니다. 기본 72dpi로 래스터화하면 512px로 키울 때 뭉개집니다.
`sharp`는 Next의 전이 의존이라 이미 설치돼 있습니다.

**서비스워커는 넣지 않습니다.** 오프라인 프리캐시는 낡은 JS 번들을 살려 두는 장치인데 그
번들에는 스키마 마이그레이션이 없습니다 — 캐시된 구버전 코드가 최신 저장 데이터를 읽는 것이
이 앱에서 가장 위험한 실패 모드입니다. 게다가 오프라인이어도 로그인과 온라인 대전이 안 되므로
실이득도 작습니다.

## 데이터 백업

**설정 → 데이터 백업**에서 팀·리그·경기 기록·설정을 JSON 파일 하나로 내보내고 가져옵니다.
기록과 클립은 원래 이 브라우저에만 있고 게스트는 팀과 리그도 로컬이 전부라, 브라우저를
바꾸면 통산 기록이 통째로 사라지는데 되돌릴 방법이 없었습니다.

가져오기는 **다른 계정·다른 기기로의 이전까지** 지원합니다. 주 용도가 게스트 → 구글 로그인
승격이라 그냥 넣으면 두 가지가 깨집니다.

1. `ownerUid`가 남의 것이라 팀·리그 목록의 소유자 필터에 전부 걸러지고, 다음 새로고침에
   통째로 사라집니다.
2. 원래 주인의 문서가 같은 브라우저에 남아 있으면 id가 부딪혀 서로를 덮어씁니다.

그래서 소유자를 바꾸고 **부딪히는 id만** 새로 만듭니다. 안 부딪히면 id를 그대로 두므로
같은 계정 복구는 멱등입니다. 팀 id를 품은 자리는 일정·포스트시즌 대진·우승팀·박스스코어까지
열두 군데로 흩어져 있어, 하나라도 빠지면 리그가 조용히 깨집니다 —
`backup.test.ts`가 그 열두 곳을 이름으로 하나씩 짚습니다. 특히 `LeagueTeamRef.ownerUid`를
빠뜨리면 리그가 목록에는 보이는데 "내 팀이 참가하지 않은 리그"로 잠깁니다.

**`Player.id`는 바꾸지 않습니다.** 팀 문서 안에서만 유효하고, 타순·로테이션과 박스스코어의
선수별 줄이 그대로 맞아떨어집니다.

그 밖의 규칙:

- 병합이 아니라 **전체 교체**입니다. "한 계정 한 팀"이 강제돼 있고 골드·인벤토리가 팀에
  붙어 있어서, 팀이 둘이 되면 지갑이 늘어납니다.
- 되돌릴 수 없는 작업이라 **누르기 직전에 지금 상태를 자동으로 한 번 내려받습니다.**
- 경기 기록만은 병합합니다 — 계정 개념이 없는 기기 전역 링버퍼라 교체하면 다른 계정으로
  치른 경기까지 날아갑니다.
- 클립은 기본 제외입니다(파일이 수 MB가 됩니다). 온라인 보상 원장은 내보내지도 가져오지도
  않습니다 — 백업으로 리셋할 수 있으면 남용 방지 장치의 존재 이유가 사라집니다.

## 저장 스키마와 마이그레이션

팀 문서에는 `schemaVersion`이 붙어 있고, 값이 맞지 않으면 **불러오지 않았습니다.** 티어·레벨을
도입할 때는 그게 옳았지만 그 뒤로 아무도 그 값을 올리지 못했습니다 — 올리는 순간 모든 유저의
팀이 사라지기 때문입니다. 그래서 이후 열두 번의 스키마 변경이 전부 "선택 필드로 조용히 추가"로
처리됐고, 진짜 파괴적 변경이 필요해지면 쓸 수 있는 수단이 없었습니다.

[migrate.ts](src/lib/game/migrate.ts)가 그 수단입니다. `TEAM_MIGRATIONS`에 `{ from, note, up }`을
한 칸씩 쌓으면 옛 문서가 목표 버전까지 따라 올라옵니다. 지금은 비어 있습니다(v2가 최신).

| 상황 | 처리 |
|---|---|
| 버전이 같음 | 그대로 |
| 버전이 낮고 업그레이더가 있음 | 한 칸씩 올린 뒤 캐시·원격에 되씀 |
| 버전이 낮고 업그레이더가 없음 | `TOO_OLD` — 목록에서 빼되 **원본은 지우지 않음** |
| 버전이 **미래** | `TOO_NEW` — 읽지도, 되쓰지도 않음 |
| 형태가 깨짐 / 변환 실패 | `CORRUPT` / `FAILED` |

**버전이 미래면 절대 손대지 않습니다.** 억지로 읽고 되쓰면 최신 기기에서 만든 팀을 열어 둔
낡은 탭이 덮어써 데이터가 실제로 사라집니다. 마이그레이션 후 원격에 되쓸 때도 `updatedAt`은
올리지 않습니다 — 형태 변환일 뿐 "새 저장"이 아니고, 올리면 기기 간 최신값 병합이 왜곡됩니다.

읽지 못한 문서는 화면 위에 **무엇이 왜 빠졌는지 배너로 알립니다.** 예전에는 팀이 그냥 사라지고
창단 화면으로 떨어져서, 사용자 입장에서는 데이터가 없어진 것처럼 보였습니다.

**리그에는 버전을 두지 않습니다.** 팀은 "못 읽으면 재창단"이라는 탈출구가 있지만 리그는 없어서,
막히면 시즌 승패·포스트시즌 대진·보상 표식이 통째로 잠깁니다. 대신 정책을 못 박습니다 —
리그는 파괴적 변경을 하지 않고, 필드를 바꿔야 하면 새 필드를 추가하고 옛 필드는 읽기 전용으로
남깁니다. 함수 안에 흩어져 있던 정규화는 `LEAGUE_NORMALIZERS` 한 곳에 모았고 전부 멱등입니다.

## Firestore 사용량

경기 중에는 Firestore에 **쓰기가 발생하지 않습니다.** 모든 게임 트래픽은 WebRTC
DataChannel로 흐릅니다. Firestore를 쓰는 시점은 다음뿐입니다.

| 동작 | 쓰기 |
|---|---|
| 팀 저장 / 훈련·성장 결과 저장 | 1 |
| 리그 생성 / 경기 결과 기록 | 1 |
| 방 생성 (offer 포함) | 1 |
| ICE 후보 교환 | 보통 5~15 (연결 후 삭제) |
| 방 입장 (answer) | 1 |
| **경기 1회당 (투구 300구 포함)** | **0** |

한 경기당 총 Firestore 쓰기는 약 10~20회 수준입니다.

## 조작

### 공격 (타격)
| 입력 | 동작 |
|---|---|
| 마우스 이동 / 방향키 | 배트 조준점 이동 |
| `Space` (투구 전) | 타석에 들어서기 → 상대가 투구 |
| 클릭 / `Space` | 일반타격 |
| `Shift`+클릭 / `A` | 강한타격 (판정 범위 좁고 파워 상승) |
| `S` | 번트 |
| 주자 버튼 | 도루 지시 (투구 전에만) |
| **터치** | 끌어서 조준 → 손을 떼면 스윙 (타격 방식은 토글 버튼) |

### 수비 (투구)
1. 구종 선택 — 직구는 모든 투수가 보유, 변화구는 선수마다 다름
2. 존 그리드를 클릭해 목표 코스 지정 (존 바깥도 가능)
3. 퀵모션 여부 선택 (주자 있을 때) → **투구!**

제구 능력치가 낮으면 노린 곳에서 벗어납니다. 스태미나가 떨어지면 구속과 제구가 함께 나빠집니다.

## 게임 시스템

### 선수

선수는 **투수와 타자로 갈려서 생성**되며 그 구분은 바뀌지 않습니다. 플레이어가 바꿀 수 있는 건
투수의 마운드 역할(선발 4명 필수 / 중간계투 / 마무리 최대 2명)과 타자의 야수 포지션 9개뿐입니다.

**창단 시에는 경기를 굴릴 최소 인원 17명만 받습니다** — 투수 7명(선발 4 · 중간계투 1 · 마무리 2)
+ 타자 10명. 불펜이 셋뿐이라 선발이 지치면 바로 아쉬워지고, 벤치 타자도 한 명뿐이라 컨디션
난조 하나에 라인업이 흔들립니다. 선수를 더 모으는 건 상점에서 합니다. CPU·리그 상대팀은
그대로 23명입니다 — 상대까지 얇아지면 후반에 불펜이 비어 난이도가 조용히 내려갑니다.

마무리를 둘까지 둘 수 있는 이유는, 마무리가 "교체 후보의 맨 뒤"라는 순서 표시일 뿐이고
같은 역할끼리는 남은 투구 여력 순으로 갈리기 때문입니다. 둘을 두면 스태미나가 넉넉한 쪽이
알아서 먼저 올라옵니다.

**타자 (포수 포함)** — 컨택 / 파워 / 선구안 / 스피드 / 수비 / 송구
**투수** — 스태미나 + **구종별로** 구속 / 제구 / 무브먼트

선수 생성은 **총량 예산제**입니다. 능력치 합계를 좁은 정규분포에서 뽑은 뒤 포지션별
가중치로 배분하므로, 무작위이면서도 압도적으로 강하거나 쓸모없는 선수가 나오지 않습니다.

### 체형

타자는 체형을 셋 중에서 고릅니다. 능력치 수치 자체는 바뀌지 않고, 경기에 쓰이는 값에만
더해집니다 — 선수단 화면에 `파워 62 +5`처럼 함께 표시됩니다.

| 체형 | 파워 | 스피드 | 특징 |
|---|---|---|---|
| 기본 | 0 | 0 | 균형 잡힌 체형 |
| 슬림 | −5 | +5 | 가벼워 발이 빠르지만 타구가 덜 뻗는다 |
| 거구 | +5 | −5 | 타구는 멀리 가지만 발이 느려진다 |

3D 모델은 몸의 두께만 달라집니다. 키와 머리 비율은 그대로입니다 — 골격 치수는 포즈·IK와
한 세트로 튜닝돼 있어서 키를 건드리면 스트라이크존 정렬과 카메라가 함께 깨집니다.

### 티어와 레벨

모든 선수는 **C등급 1레벨**에서 시작합니다. 경기에 나가면 경험치를 받아 레벨이 오르고,
레벨이 오를 때마다 **그 선수 전용 훈련 포인트**를 받습니다. 최대 레벨에 도달하면 골드를 써서
티어를 올립니다.

| 티어 | 최대 레벨 | 능력치 상한 | 구종 슬롯 | 강화 비용 |
|---|---|---|---|---|
| C | 10 | 65 | 3 | 2,000G |
| B | 20 | 78 | 4 | 8,000G |
| A | 30 | 89 | 5 | 25,000G |
| S | 40 | 99 | 6 | — |

**티어 강화는 능력치를 전혀 건드리지 않습니다.** 레벨만 1로 돌아가고 상한이 넓어질 뿐이라,
"C 10레벨의 능력치 그대로 B 1레벨"이 됩니다. 능력치는 오직 훈련 포인트를 써야 오릅니다.

실제 상한은 **티어 상한과 선수 고유 잠재력 중 낮은 쪽**입니다. 잠재력이 70인 선수는 A등급이
돼도 70에서 막히므로, 같은 S등급 안에서도 개인차가 남습니다.

### 구종

| 구종 | 특징 | 습득 |
|---|---|---|
| 직구 | 가장 빠르고 제구가 쉽다 | 전원 기본 보유 |
| 투심 / 싱커 | 가라앉는다, 땅볼 유도 | 골드 |
| 커터 / 슬라이더 | 옆으로 꺾인다 | 골드 |
| 커브 / 포크볼 | 낙차가 크다 | 골드 |
| 체인지업 | 타이밍 교란 | 골드 |
| 너클볼 | 궤적이 무작위, 제구 매우 어려움 | 골드 |

보유할 수 있는 구종 수는 티어가 정합니다(C 3 · B 4 · A 5 · S 6). 슬롯이 차면 티어를 올려야
하나 더 익힐 수 있습니다.

**새 구종은 훈련 포인트가 아니라 골드로 삽니다.** 훈련 포인트는 레벨업으로만 들어오는
희소 자원이라, 구종 습득까지 거기서 빼면 "능력치를 올릴지 구종을 배울지"가 아니라
"구종은 못 배운다"가 됩니다. 비용은 난이도와 이미 보유한 구종 수에 비례해
4번째 구종이 2,550~6,630G, 6번째가 3,600~9,360G 선입니다.

### 훈련

훈련 포인트는 **레벨업으로만** 들어오고 **능력치에만** 씁니다. 능력치가 높을수록 1 올리는
비용이 급격히 커지고, 상한에 닿으면 티어를 강화해야 다시 자랍니다.

레벨업 1회가 주는 포인트는 C 12 · B 18 · A 24 · S 30입니다. 능력치 1을 올리는 데 값 50에서
4P, 70에서 12P가 드니 레벨 하나가 대략 능력치 3~4포인트입니다. 이보다 낮게 잡으면 커리어
전체(96레벨)를 돌아도 티어 상한에도 잠재력에도 닿지 못해 상한이라는 개념 자체가 장식이 됩니다.

### 투수 스태미나 (경기 간 이월)

투수의 스태미나는 **경기가 끝나도 소모된 상태로 남습니다.** 등판하지 않은 경기마다 1/3씩
회복하므로, 완전히 지친 선발도 **3경기를 쉬면 가득 찹니다.** 로테이션은 경기마다 한 칸씩
돌고, 피로가 남은 채로 올라오면 그만큼 이미 지친 상태에서 시작합니다. 능력치 좋은 선발
한 명으로 모든 경기를 돌릴 수 없게 하려는 장치입니다.

### 컨디션 난조 (부상)

투구 수가 한계를 크게 넘기면 낮은 확률로 **투구 과부하**(2~5경기), 사구를 맞으면 **타박**
(1~3경기)이 생깁니다. 회복은 경기를 한 판 끝낼 때마다 하루씩 줄어듭니다.

**출전을 막지는 않습니다.** 대신 경기 중 모든 능력치가 **남은 경기 수에 비례해** 깎입니다
(1경기당 5%, 최대 25%). 갓 다쳤을 때가 가장 나쁘고 회복이 가까울수록 옅어져서, 낫는 중이라는 게
숫자로 보입니다. 타자 한 명이 다치면 팀 득점이 3~5% 줄어드는 정도입니다(180경기 실측).

출전 금지가 아니라 페널티인 이유는 **회복이 경기 종료로만 진행되기 때문**입니다. 부상자를
막아 버리면 타자가 빠듯한 로스터에서 라인업 9명을 못 채워 경기가 잠기고, 경기를 못 하니 부상도
영영 낫지 않고, 골드도 못 벌어 선수를 살 수도 없는 상태에 갇힙니다.

보정은 경기용 로스터를 만드는 `engine.toTeamInGame` 한 곳에서만 겁니다. 능력치를 읽는 쪽마다
보정을 걸면 반드시 어딘가 새고, 그때는 "타격만 깎이고 발은 멀쩡한" 반쪽이 됩니다
(`batting.effSpeed` 주석과 같은 이유). 저장된 팀의 능력치는 건드리지 않습니다.

### 경기 보상

경기는 **선수별 경험치와 팀 골드**를 줍니다. 아이템은 경기에서 나오지 않습니다.

- 출전한 선수만 받습니다. 타자는 안타·홈런이, 투수는 이닝과 탈삼진이 추가분의 대부분입니다.
- 난이도(이지 0.8 ~ 프로 1.6)와 승패(승 1.3 / 무 1.0 / 패 0.8)가 배수로 곱해집니다.
- 져도 0은 아닙니다 — 0이면 질 것 같을 때 나가 버리는 편이 이득이 되기 때문입니다.

**온라인 대전(1:1 · 2대2 · 릴레이)** 은 시즌 기록을 남기지 않고, 득점·완봉 보너스도 난이도
배수도 없습니다 — 상대가 사람이라 난이도라는 개념 자체가 없고, 점수에 값을 매기면 그게 곧
승부조작의 대가가 되기 때문입니다. 승패라는 결과 하나만 봅니다. 하루 총량도 골드 1,200 ·
경험치 2,500으로 막습니다 (`onlineCap.ts`). 남은 한도는 선수단 화면 상단에 표시되고 매일
자정(로컬 시간)에 다시 채워집니다. 원장은 브라우저별 로컬 저장이라 서버 검증은 아니며,
캐주얼한 반복 파밍을 막는 선까지가 목적입니다.

### 아이템

아이템이 나오는 유일한 경로는 **리그입니다** — 정규 시즌 1~3위와 포스트시즌 우승·준우승.

| 아이템 | 효과 |
|---|---|
| 경험치보충제 (소/중/대/특대) | 선수 한 명에게 경험치 60 / 200 / 550 / 1,000 (레벨 1 기준 약 2 / 4 / 8 / 10레벨) |
| 능력치초기화권 | 쓴 훈련 포인트와 구종 습득 골드를 전액 환급하고 능력치를 처음 상태로 되돌린다 |
| 부상치료제 | 컨디션 난조를 즉시 없앤다 |
| 스테미나회복제 | 누적 피로를 완전히 없앤다 (투수 전용) |

골드는 정규 1위 6,000 · 2위 3,000 · 3위 1,500, 우승 8,000 · 준우승 2,500입니다
(총량은 포스트시즌 도입 전과 같습니다). 능력치초기화권과 경험치보충제(특대)는 **우승에서만**
나옵니다 — 정규 1위로 들어가도 단기전에서 지면 손해가 되도록 한 배분입니다.

### 상점 — 영입과 방출

창단 로스터 17명 말고 선수를 더 얻는 유일한 경로입니다. 뽑기 전에 **투수/타자를 고릅니다.**

| 배너 | 비용 | 확률 |
|---|---|---|
| 일반 뽑기 | 5,000G | C 50% · B 40% · A 10% |
| 프리미엄 뽑기 | 45,000G | B 50% · A 40% · S 10% |

뽑은 선수는 **그 티어의 1레벨**이고, 능력치는 **직접 키웠을 때와 같은 수준**입니다. 티어 강화가
능력치를 안 건드리는 구조라 "그 티어 1레벨의 능력치"라는 기준이 따로 없었기 때문에, 그 티어까지
자연스럽게 성장했다면 받았을 훈련 포인트(B 108 · A 450 · S 1,146)를 실제 훈련 곡선으로 미리
써 준 상태로 만듭니다. 구간마다 그때의 상한을 적용하므로 결과가 육성 경로와 정확히 맞습니다.

| 티어 | 능력치 합 | 평균 | 잠재력 |
|---|---|---|---|
| C | 300 | 50 | ~82 |
| B | 327 | 54.5 | ~87 |
| A | 380 | 63.3 | ~93 |
| S | 442 | 73.7 | ~96 |

상위 티어의 진짜 값어치는 **잠재력**입니다. 창단 선수는 평균 82라 C부터 갈아 올려도 S 상한을
다 쓰지 못하지만, 뽑은 S는 96 근처라 그 천장에 닿습니다. 투수는 티어 구종 슬롯을 가득 채워
나옵니다(S면 6구종). 다만 역할은 **중간계투**로 들어옵니다 — 선발은 정확히 4명이어야 해서,
그냥 넣으면 로스터 검증이 즉시 막힙니다.

방출하면 티어·레벨에 따라 골드를 돌려받습니다(C Lv.1 200G ~ S Lv.40 18,880G). 타순·로테이션에
등록된 선수, 선발 투수, 그리고 타자 9명 · 투수 6명 하한에 걸린 경우는 방출할 수 없습니다.
**어떤 배너에서 무엇이 나오든 즉시 되팔면 반드시 손해**입니다 — 기댓값이 아니라 티어별
최댓값으로 그렇게 맞춰 두어(일반 최대 4,200 < 5,000, 프리미엄 최대 14,200 < 45,000), 운 좋은
뽑기를 되파는 전략이 아예 생기지 않습니다. 이 조건은 테스트로 고정돼 있습니다.

### 경기 중 교체

투수 교체 외에 **대타 · 대주자 · 대수비**를 쓸 수 있습니다. 타순에 들어 있지 않은 벤치 타자
중에서 고르며, 한 번 교체돼 나간 선수는 그 경기에 다시 나오지 못합니다.
지금은 CPU 대전과 리그에서만 쓸 수 있습니다 (온라인은 프로토콜 확장이 필요합니다).

### 좌우 상성

같은 손끼리 붙으면(좌투–좌타) 변화구가 몸쪽에서 바깥으로 달아나 치기 어렵고, 엇갈리면
공이 몸쪽으로 들어와 보기 편합니다. 배트 판정 반경 하나에만 곱해서 겁니다 — 헛스윙률과
타구의 질이 함께 흘러나오는 유일한 지점이라, 여러 곳에 나눠 걸면 180경기 시뮬레이션으로
되돌리기가 불가능해집니다.

**스위치히터는 언제나 투수 반대편에 섭니다.** 좌우를 읽는 곳은 판정·AI·몸에 맞는 공·3D
배치까지 전부 `batting.effectiveBatSide` 하나를 거칩니다. 각자 `bats`를 읽으면 "판정은
좌타인데 화면에서는 우타석에 선" 반쪽이 반드시 생깁니다.

선수단 화면에 좌투/우투 상대 타율이 함께 표시되므로, 대타를 고를 때 능력치 말고 볼 것이
생깁니다.

### 경기 기록과 다시 보기

경기가 끝나면 **박스스코어**가 남습니다 — 이닝별 득점, 개인 성적, 득점 장면의 실황 텍스트.
새로 계산하는 값은 없고 엔진이 경기 내내 채워 둔 것을 옮겨 담을 뿐입니다.

홈런과 역전 장면은 **다시 보기 클립**으로 함께 저장됩니다. 엔진이 결정론적이라
"투구 직전 상태 + 그때의 커맨드" 두 개면 그 플레이가 그대로 재현되므로, 재생은
`resolvePitch`를 한 번 더 부르는 것뿐입니다. 저장하기 전에 실제로 한 번 재생해 보고 원래
결과와 같을 때만 남깁니다 — 실제와 다른 장면을 보여 주는 다시 보기는 없느니만 못합니다.

기록은 **이 브라우저에만** 남습니다(최근 60경기, 클립은 최근 3경기). Firestore에 쓰면
README가 약속한 "경기 1회당 쓰기 0"이 깨지기 때문입니다.

### 중단된 경기 이어서 하기

**CPU 대전과 리그 경기**는 도중에 나가도 그 자리에서 다시 시작할 수 있습니다. 한 경기가
30분이 넘는데 화면을 벗어나면 통째로 사라졌고, 리그라면 일정이 `SCHEDULED`로 남아 처음부터
다시 쳐야 했습니다.

저장은 **투구 결과가 확정된 직후**에 일어납니다. 투구 전 상태를 저장하면 결과가 마음에 들지
않을 때 나갔다 들어오는 것만으로 그 타석을 무를 수 있는데, 리그 성적이 걸린 경기에서 그건
기능이 아니라 구멍입니다. 되살릴 때는 엔진 상태(카운트·주자·선수별 기록·RNG)에 더해
**AI 전용 난수 상태와 실황 로그**까지 함께 돌립니다 — 시드를 처음부터 다시 감으면 CPU가 같은
자리에서 같은 판단을 반복합니다.

- 슬롯은 **리그 일정마다 하나**, CPU 대전은 통틀어 하나입니다. 계정별로 최대 3개까지 들고
  있고 넘치면 오래된 것부터 버립니다.
- **다시 보기 클립은 담지 않습니다.** 클립 하나가 `GameState`를 통째로 품고 있어(수십 KB)
  매 투구 쓰기가 다섯 배로 불어납니다. 중단한 경기의 다시 보기를 잃는 것이 팀 문서를
  5MB 한계 밖으로 밀어내는 것보다 낫습니다.
- 경기가 끝나면 슬롯을 **비웁니다.** 끝난 경기를 되살릴 수 있으면 보상을 다시 받는 길이 됩니다.
  같은 이유로 다른 계정·다른 팀의 저장, 30일이 지난 저장, 자동 진행으로 이미 처리된 리그
  경기의 저장은 거절합니다.
- 온라인 1:1 · 2대2 · 릴레이는 저장하지 않습니다. 판정 권한과 P2P 연결, 상대의 남은 시간이
  걸려 있어 나 혼자 되살릴 수 있는 상태가 아닙니다. 연습 타석은 이어서 할 상태가 없습니다.

경기 중 `나가기`는 저장하고 나갈지 포기할지를 묻습니다. 저장되는 줄 모르고 나가면 포기와
구분이 안 되고, 반대로 그만두고 새로 시작할 길도 있어야 하기 때문입니다.
기록과 마찬가지로 **이 브라우저에만** 남습니다(`ab:suspendedMatches`).

### 포스트시즌

정규 일정을 다 치르면 순위대로 단기전이 붙습니다. 5팀 이상이면 상위 4팀이 준결승
(5전 3선승, 1-4 / 2-3)을 치르고 결승(7전 4선승)에 오릅니다. 4팀 이하면 상위 2팀이 곧바로
결승(5전 3선승)을 치릅니다. 상위 시드가 홈을 더 많이 갖습니다(2-3-2).

**새 시스템이 아니라 이미 있는 압력을 처음으로 쓰는 것에 가깝습니다.** 로테이션은 경기마다
한 칸씩 돌고 투수 피로는 경기 사이에 이월되므로, 선발 4명으로 7경기를 짜는 문제가 저절로
생깁니다. 마침 4명 × 3경기 휴식이 완전 회복 주기와 정확히 맞물립니다.

보상은 정규 순위와 우승으로 나뉘며 **총 지급량은 예전(21,000G) 그대로**입니다.

| 항목 | 골드 |
|---|---|
| 정규 1위 / 2위 / 3위 | 6,000 / 3,000 / 1,500 |
| 우승 | 8,000 |
| 준우승 | 2,500 |

능력치초기화권과 경험치보충제(특대)는 이제 **우승에서만** 나옵니다. 1위로 들어가도 단기전에서
지면 손해가 되도록 맞춘 배분입니다.

### 시즌과 통산 기록

`Player.season`은 예전에 이름만 "시즌"이고 실제로는 선수를 만든 순간부터 영구히 쌓이기만
했습니다. 이제 리그가 끝나면 **시즌 마감**을 눌러 경계를 그을 수 있습니다.

마감하면 이번 시즌 기록이 통산으로 넘어가고 시즌 기록이 0으로 돌아갑니다. 시즌별 성적은
최근 5시즌까지 남습니다. **능력치·레벨·티어는 건드리지 않습니다** — 시즌이 바뀐다고 키운
선수가 약해지면 그건 다른 게임입니다.

마감 전 화면에는 그 시즌의 타이틀(타율·홈런·타점·도루·다승·방어율·탈삼진·MVP)이 뜹니다.
타율왕과 방어율왕에는 규정 타석(3.1타석/경기)과 규정 이닝이 걸립니다 — 없으면 1타수 1안타가
타율 1.000으로 1위가 됩니다.

### 리그 개인 기록

리그 화면의 **개인 기록**은 CPU 팀 선수까지 포함한 부문별 상위 5명입니다.

자동 시뮬레이션은 예전부터 CPU 선수의 시즌 기록을 전부 계산하고 있었지만 호출하는 쪽이
스코어만 꺼내 쓰는 바람에 통째로 버려졌습니다. 지금은 그 델타를 리그 문서에 박제된
CPU 팀(`League.cpuTeams`)에 그대로 누적합니다 — 새 필드가 필요 없고, 무엇보다 **내 팀은
거기 없으므로** 팀 문서와의 이중 계산이 조건문이 아니라 데이터 배치로 막힙니다.

**규정 타석은 그 선수 자기 팀의 경기 수로 잽니다.** 리그 최다 경기 팀으로 통일하면
포스트시즌에서 무너집니다 — 결승까지 간 팀이 최대 7경기를 더 치르므로, 통일하면 일찍
탈락한 팀 타자가 전부 규정 미달로 사라집니다.

타이틀 수상자와 리더보드 1위는 같은 부문 명세(`season.TITLE_SPECS`)를 읽으므로 어긋날 수
없습니다. 내 팀 기록에는 이 리그 밖에서 치른 CPU 대전도 들어 있어 CPU와 완전히 대칭은
아니며, 화면에 그렇게 적어 두었습니다.

기록을 쌓기 시작하면서 **CPU 팀의 로테이션도 함께 돌립니다.** `rotationIndex`를 올리는
코드는 경기 보상 정산 하나뿐이고 그건 내 팀에만 돌아서, CPU 팀은 창단 이후 영원히 1선발만
냈습니다. 그대로 두면 다승·방어율·탈삼진 순위가 팀당 한 명으로 굳습니다.

### 연습 타석

타이밍 게임인데 연습할 곳이 없었습니다. `/practice`는 카운트도 아웃도 없이 계속 칠 수 있고,
스윙마다 **얼마나 빨랐는지·늦었는지를 ms로** 알려 줍니다. 이 값은 예전부터 매 스윙 계산되고
있었지만(`SwingCommand.timingMs`) 화면에 한 번도 나오지 않았습니다.

누적해서 "전반적으로 빠름" 같은 버릇도 보여 줍니다. **보상은 없습니다** — 판정 없는 무한
타석에 경험치나 골드를 걸면 그게 곧 최적 파밍 경로가 되기 때문입니다.

### 터치 조작

마우스는 커서를 옮겨 조준해 두고 클릭으로 치지만, 손가락은 화면에 닿는 그 순간이 곧
조준이라 같은 동작에 스윙까지 묶으면 조준 자체가 불가능합니다. 터치에서는 **끌어서 조준하고
손을 뗄 때** 칩니다 — 투수가 와인드업하는 동안 겨누고 공이 올 때 놓으면 됩니다.
Shift가 없으므로 타격 방식은 패널의 토글 버튼을 따릅니다.

### 규칙

실제 야구 규칙을 따릅니다 — 3스트라이크/4볼, 2스트라이크 이후 파울은 스트라이크 아님
(단 번트 파울은 삼진), 포스아웃·병살·야수선택, 태그업 희생플라이, 인필드 플라이,
폭투, 몸에 맞는 공, 끝내기, 연장(최대 3이닝).

**피치 클락 20초** — 투구 전 대기가 20초를 넘기면 위반입니다. 투수가 넘기면 자동 볼,
타자가 넘기면(CPU전에서 타석에 들어서지 않을 때) 자동 스트라이크가 선언됩니다.
남은 시간은 상단 카운트 옆에 표시되고, 타자·투수 교체나 다음 투구마다 다시 감깁니다.
온라인에서는 호스트만 위반을 판정합니다. 시간은 `PITCH_CLOCK_SEC`
([constants.ts](src/lib/game/constants.ts))에서 바꿉니다.

**설정에서 조절 가능**: 효과음·관중석·배경음 각각 켜기/끄기 및 볼륨, 정규 이닝(7/9),
콜드게임(발동 이닝·점수차), 지명타자, 투구 체감 속도, 카메라 흔들림.

**카메라 흔들림** — 배트에 맞는 순간 시선이 짧게(0.42초) 흔들리고 타구속도에 비례해 커집니다.
위치가 아니라 각도를 흔들기 때문에 타자 시점이든 스카이뷰든 같은 세기로 전달됩니다.
세기는 타구속도만 보고 정하므로 안타인지 아웃인지를 미리 알려 주지 않습니다.

### 사운드

투구, 포구, 타격, 번트, 헛스윙, 안타/홈런 관중 환호와 심판 콜은 Web Audio API로
재생합니다. 경기 외 화면의 배경음은 아래 위치에 직접 넣은 MP3 파일을 반복 재생합니다.

```text
public/audio/bgm/menu.mp3
```

파일이 없어도 게임은 정상 동작하며 배경음만 재생되지 않습니다.

## 밸런스 검증

엔진은 결정론적 시드 기반이라 헤드리스로 대량 시뮬레이션할 수 있습니다.
`balance.test.ts`가 180경기(=360 팀·경기)를 돌려 아래 지표가 범위를 벗어나면 실패합니다.

| 지표 (팀·경기당) | 이 게임 | MLB |
|---|---|---|
| 득점 | 4.31 | 4.5 |
| 안타 | 8.50 | 8.7 |
| 홈런 | 1.18 | 1.15 |
| 2루타 | 1.76 | 1.65 |
| 3루타 | 0.14 | 0.14 |
| 볼넷 | 2.57 | 3.2 |
| 삼진 | 8.80 | 8.5 |
| 타율 | .245 | .248 |
| 도루 | 0.52 | 0.5~0.6 |
| 도루 실패 | 0.24 | 0.2 |

좌우 상성이 붙은 뒤의 값이다. `batting.test.ts`가 같은 180경기에서 좌우 스플릿도 함께
재는데, 동측(좌투-좌타) 타율 .239 / 이측 .257로 실제 MLB의 15~25포인트 차와 같은 폭이다.

**도루도 지표에 넣는다.** 넣기 전까지 `ai.decideSteal`의 문턱값이 창단 로스터가 닿을 수 없는
곳(정규화 speed 0.62 ≈ 능력치 61, 타자 speed 분포의 상위 15%)에 있어 도루가 팀·경기당
0.13까지 말라 있었는데, 지표에 없으니 아무도 몰랐다. 시도 확률은 발이 빠를수록 가파르게
붙는다 — 이 엔진의 도루는 주파 시간 대 (딜리버리 + 비행 + 포수 팝타임) 경주라 성공률이
속도 40대 36% · 50대 52% · 60대 74%로 갈리고, 그보다 느린 주자를 뛰게 하면 도루가 아니라
아웃이 늘기 때문이다.

타구 물리는 실제 항력·양력 계수를 사용합니다 (186km/h·28° → 147m).

자동 시뮬레이션도 지친 투수를 불펜으로 교체합니다. 이게 없으면 선발이 9이닝을 완투하며
140구를 던지고, 후반에 제구가 무너져 볼넷과 득점이 실제보다 크게 부풀려집니다.

### 경제 회귀 검증

`balance.test.ts`가 재는 것은 **한 경기 안에서 무엇이 몇 번 일어나는가**입니다. 골드와 성장이
시즌을 거치며 어디에 도달하는지는 아무도 재고 있지 않았습니다 — 도루가 팀·경기당 0.13까지
말라 있었는데 지표에 없어서 아무도 몰랐던 것과 같은 종류의 사각지대입니다.

`economy.test.ts`가 창단 로스터로 **3시즌 72경기**를 헤드리스로 돌립니다. 매 경기
`simulateGame → applyMatchResult → 훈련·강화`를 실제 게임 루프와 같은 순서로 엮고, 시즌 끝에는
그 시즌 승률로 순위 보상을 붙입니다. 상대는 같은 창단 로스터로 고정합니다 — 시즌마다 세게
만들면 트레드밀이 되어 팀이 커도 승률이 그대로고, 순위 보상이 한 번도 발생하지 않습니다.

| 지표 | 실측 | 의미 |
|---|---|---|
| 경기당 골드 | 359 | 승패 배수가 섞인 평균 |
| 한 시즌 수입 | 10,110 | A→S 강화 한 번(25,000)의 절반 이하 |
| 시즌 승수 | 8 → 11 → 13 | 훈련·강화가 경기력에 닿는다 |
| S 하나까지 | 약 285경기 | 경험치 곡선에서 파생 |
| 골드로만 보면 | 약 83경기 | **병목은 골드가 아니라 경험치다** |
| 커리어 수입 / 로스터 전원 S | 0.20 | 1을 넘으면 육성 선택이 사라진다 |
| 버려진 경험치 비율 | 0.58 | 0이면 티어 게이트가 아무도 못 막고 있다는 뜻 |

**어떤 상수의 값도 다시 단정하지 않습니다.** 상수에서 파생된 "몇 경기 만에 / 몇 배만큼"만
봅니다. 그래야 `progression`·`shop` 테스트와 중복되지 않고, 상수를 조정해도 곡선이 그대로면
통과합니다. 아이템은 넣지 않습니다 — 경험치보충제를 넣는 순간 "언제 누구에게 쓰느냐"는
정책이 지표에 섞입니다.

감도는 고의 회귀로 확인했습니다. 기본 골드를 3배로 올리면 단정 3개가, 경험치 곡선을 절반으로
줄이면 2개가, B→A 강화 비용을 10배로 올리면 1개가 깨집니다.

### 온라인 대전 아키텍처

**호스트 권위(host-authoritative)** 모델입니다.

```
게스트                     호스트
  │   HELLO(팀) ─────────────▶│
  │◀───────────── HELLO(팀)   │
  │◀───────────── START(초기 상태)
  │                           │
  │  (수비 시) PITCH ────────▶│
  │◀──────── PITCH_GO(구종·코스)   ← 양쪽이 같은 시드로 같은 궤적을 그린다
  │  (공격 시) SWING ───────▶│
  │◀──────── RESULT(판정 + 상태 스냅샷)
```

엔진이 시드 기반 결정론이므로 게스트도 같은 상태에서 같은 결과를 재현·검증할 수 있고,
호스트만 판정하므로 상태가 갈라지지 않습니다.

### 2대2 올스타전

네 명이 두 팀으로 나뉘어 붙습니다. 같은 편 두 사람이 **각자 자기 팀에서** 선수를 반씩 골라 와
하나의 올스타 팀을 만들고, **타석에 자기 선수가 섰을 때만** 조작합니다.

| 항목 | 규칙 |
|---|---|
| 선수 선발 | slot 0이 야수 5명, slot 1이 야수 4명 + 각자 투수 2명 |
| 타순 | 두 사람을 번갈아 배치 (slot 0 → 1·3·5·7·9번, slot 1 → 2·4·6·8번) |
| 공격 조작 | 타석에 선 선수의 주인만. 팀원 타석에는 관전 |
| 수비 조작 | 마운드에 선 투수의 주인만. 자기 불펜을 올리면 조작권이 넘어온다 |
| 선발 투수 | 두 사람이 낸 투수 4명을 섞어 **무작위** 추첨 (시드 기반) |
| 지명타자 | 항상 사용 (라인업이 야수 9명이므로) |

연결은 호스트를 허브로 하는 **별 구조**입니다. 게스트끼리는 직접 연결하지 않고
모든 메시지가 호스트를 거쳐 중계되므로, 1:1과 같은 호스트 권위 모델이 그대로 유지됩니다.

```
        게스트A
          │
게스트C─호스트─게스트B
```

1:1은 방 문서에 offer/answer를 한 쌍 두지만, 2대2는 게스트가 3명이라
`rooms/{roomId}/peers/{uid}` 문서를 게스트마다 만들고 **게스트가 offer를, 호스트가 answer를**
씁니다. 덕분에 호스트가 몇 명이 들어올지 미리 알 필요가 없습니다.

경기 중 누군가 연결이 끊기면 호스트가 그 사람의 선수를 인계받아(`PARTY_OWNERS`) 경기가 멈추지
않게 합니다.

### 2~7인 릴레이 타격 대결

개인전이며, 한 라운드에는 입장 순서상 한 명만 투수를 맡고 나머지 참가자가 각 1타석을
진행합니다. 모든 참가자의 투구 기회를 맞추기 위해 10라운드 이내에서 현재 인원수의 배수만
선택할 수 있습니다. 일반 안타·볼넷·사구는 1점, 홈런은 3점이며 수비와 주루는 사용하지 않습니다.

호스트가 모든 투구·스윙 판정과 순환 상태를 확정합니다. 입력에는 `turnId`와 `pitchSeq`를 넣어
늦거나 중복된 명령을 거부하며, 경기 중 기권자는 이후 차례와 순위에서 제외합니다. 현재 투수가
기권하면 그 투수 라운드에서 아직 확정되지 않은 점수만 롤백합니다.
